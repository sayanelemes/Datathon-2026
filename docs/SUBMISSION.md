# 2MP — материалы для сдачи (ForteBank Datathon 26)

> Заполнить перед отправкой: адрес сервиса, адрес API, ключ, итоговые метрики из `tools/eval_api.py`.

| | |
|---|---|
| Сервис (интерфейс) | `https://…` |
| API | `https://…/api/v1/analyze`, `https://…/api/v1/jobs/{job_id}` |
| Ключ | передаётся отдельно, заголовок `X-API-Key` |

## 1. Как пользоваться

1. Откройте сайт, перетащите запись (.mov/.mp4) и нажмите «Проверить запись».
2. Прогресс показывает этапы анализа (обычно 1,5–3 минуты).
3. Итог: «Нарушение не обнаружено» или «Обнаружены признаки возможных нарушений».
4. По каждому найденному моменту — тип, время, три кадра (ключевой — с рамкой и увеличением), что видно, пункт нормы, уверенность модели.
5. Кривая подозрительности под видео показывает всю запись; клик — переход к моменту. Во время просмотра на видео отображаются рамки людей (кассир, клиент); в момент нарушения рамка кассира становится красной.
6. Проверяющий подтверждает или отклоняет каждый момент и формирует акт (печать/PDF).

Запуск — см. `README.md`.

## 2. Архитектура

```
Жюри (API, ключ) ─┐                    ┌─ очередь с приоритетом: жюри → сайт (память или Redis)
Браузер (сайт) ───┴─► HTTPS ─► FastAPI/uvicorn: API по ТЗ + интерфейс, проверка файла, лимиты сайта
                         │
                         ▼  воркер (2 видео одновременно, лимит 5 мин от загрузки)
  1. Зона кассы     Qwen3-VL находит рабочее место кассира → дальше анализируется крупный план
  2. Просмотр       всё видео окнами 4 с (шаг 2 с, 8 кадров) → оценка каждого окна
  2б. Следопыт      параллельно: YOLOX (люди, телефоны, предметы) + RTMPose + ByteTrack, зоны, роли
                    кассир/клиент, Rule Engine (передача, телефон, кассир ушёл, посторонний в служебной зоне,
                    рука под столом) → кандидаты и детерминированные нарушения
  3. Кандидаты      подозрительные моменты из просмотра (2) и Следопыта (2б)
  4. Перепроверка   каждый кандидат: 12 кадров за 5 с, подсказка, 2 независимых голосования
  5. Решение        подтверждено большинством ИЛИ очень уверенный просмотр (полнота важнее)
  6. Доказательства кадры t−1,5 / t / t+1,5 с, рамка объекта, норма: Legal-RAG по тексту Правил НБРК № 231
                         │
                    vLLM (127.0.0.1:18001, снаружи недоступен) — Qwen3-VL-8B-Instruct-FP8, локально
       Сервер: RunPod, 1× NVIDIA L4 24 ГБ (start.sh l4) · или docker compose: api + worker + vllm + redis
```

Принципы:
- **Локальность.** Все модели работают внутри сервиса; vLLM слушает только localhost; веса загружаются один раз, далее `HF_HUB_OFFLINE=1` — анализ работает без интернета. Облачные AI-сервисы не используются ни на одном шаге.
- **Нормы не генерируются моделью.** Модель выбирает только идентификатор типа из каталога `configs/violations.yaml` и номер фрагмента из найденных в нормативной базе (`legal_base/`, текст с adilet.zan.kz); документ, пункт, URL и дословную цитату подставляет код из текста документа. Нет уверенности — `legal_reference = null`. Выдуманных ссылок быть не может.
- **Полнота важнее.** Порог «подозрительно» низкий; момент перепроверяется дважды; при отсутствии подтверждения очень уверенный сигнал всё равно выводится.
- **Надёжность.** Лимит 240 с на видео от момента загрузки; при нехватке времени решение принимается по просмотру без перепроверки; сбой одного запроса не ломает анализ; недоступность модели — явная ошибка `failed`; сторож перезапускает vLLM и сервис, прерванные задачи продолжаются сами.
- **Развитие.** Тот же код запускается в контуре банка (`docker compose up -d` или `start.sh <профиль>`); новый тип нарушения — запись в `configs/violations.yaml` и абзац нормы в `legal_base/`, без переобучения; другая камера — `configs/camera_*.yaml`.
- **Устойчивость к ракурсу.** Модель не обучена под конкретную камеру; зона кассы находится заново на каждом видео.
- **Конфиденциальность.** Лица не распознаются и не идентифицируются; роли (кассир, клиент, инкассатор) определяются по положению и действиям.

## 3. Модели

| Модель | Роль | Лицензия |
|---|---|---|
| Qwen3-VL-8B-Instruct-FP8 (Alibaba, официальная FP8) | понимание видео: зона, оценка окон, перепроверка, описание, рамка | Apache 2.0 |
| RTMPose + YOLOX COCO (OpenMMLab / Megvii, через rtmlib, ONNX Runtime) | точки тела и рук, люди, телефоны и предметы | Apache 2.0 |
| ByteTrack (собственная реализация алгоритма) | трекинг людей между кадрами | — |
| Redis 7.2 (только docker compose) | очередь задач | BSD-3 |
| vLLM | локальный сервер модели | Apache 2.0 |
| OpenCV, FastAPI, Starlette, uvicorn, pydantic | видео, веб, схемы | Apache 2.0 / MIT / BSD |

Дообучение моделей не выполнялось: на ~40 роликах это ведёт к переобучению и ухудшает работу на новых типах и другом ракурсе. Знания о датасете используются через каталог правил и промпты, подобранные на обучающей части датасета.

## 4. Нормативные источники и сопоставление

Основной источник — **Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей в банках второго уровня, филиалах банков-нерезидентов Республики Казахстан, Национальном операторе почты и юридических лицах, исключительной деятельностью которых является инкассация банкнот, монет и ценностей**, утв. постановлением Правления Национального Банка РК № 231 от 29.11.2019 (рег. в МЮ РК № 19680), ред. с изменениями на 12.07.2026. Источник: adilet.zan.kz (текст сверен 17.10.2026 по зеркалу zakon.uchet.kz);
выдержка пунктов — `legal_base/nbrk_231_kassovye_operacii.txt`.

Дополнительный источник — **Правила организации охраны и устройства помещений банков второго уровня…**,
утв. постановлением Правления НБРК № 14 от 24.02.2020 (рег. № 20075); на них ссылается п. 5 Правил № 231.
Используются п. 8 (кассовый узел изолирован) и пп. 1 п. 16 (касса — отдельный вход с закрывающейся на замок дверью).

| Тип (id) | Что видно на видео | Норма |
|---|---|---|
| Сокрытие части принятых наличных (CASH_CONCEALMENT) | кассир отделяет купюру и убирает ниже стола / в карман / вне обзора | п. 20, п. 14 |
| Принятые деньги не пересчитаны при клиенте (NO_RECOUNT_IN_FRONT) | деньги сразу убраны без пересчёта на виду | п. 20 |
| Выдача без пересчёта при клиенте (PAYOUT_NO_RECOUNT) | деньги переданы клиенту без пересчёта | п. 31 пп. 4 |
| Кассир покинул рабочее место во время обслуживания (CASHIER_LEFT_DURING_SERVICE) | клиент у кассы, кассир уходит | п. 22 |
| Наличные оставлены без присмотра (CASH_LEFT_UNATTENDED) | деньги на столе / сейф открыт, кассир отошёл | п. 20 (хранение в запираемых устройствах) |
| Мобильный телефон на рабочем месте (PHONE_AT_CASH_DESK) | смартфон в руках или на столе кассира | п. 12 |
| Сумка инкассатора принята без проверки (BAG_ACCEPTED_NO_CHECK) | сумку сразу убрали без осмотра целостности и пломбы | п. 24 |
| Вскрытие сумки без инкассатора (BAG_OPENED_NO_COLLECTOR) | сумка вскрыта в отсутствие работника инкассации | п. 25 |
| Посторонний в зоне хранения ценностей (UNAUTHORIZED_PERSON) | посторонний за столом кассира / у сейфа | п. 75 Правил № 231; п. 8, пп. 1 п. 16 Правил № 14 |
| Иное подозрительное действие с наличными (OTHER) | иное явно подозрительное действие с ценностями | п. 14 |

Формулировки норм в каталоге — близко к тексту актов; цитата в `legal_reference` берётся дословно из `legal_base/`
(код проверяет, что она есть в тексте). Пункты, для которых нужен невидимый факт (п. 25 — «при нарушении
целостности сумки»), описываются как признак возможного нарушения; вывод о самом факте — за проверяющим.

Связь «источник → нарушение → фрагмент» показывается в каждой карточке результата: «что видно» (наблюдение модели), «какое требование может быть нарушено» (пункт и документ), кадры и таймкод.

## 5. Таймкод

- Таймкод — кадр, который модель при перепроверке указала как самый показательный.
- Для нарушений «по бездействию» (например, сумка принята без осмотра) — момент, когда обязательное действие должно было произойти (передача сумки).
- Кадры-доказательства: ключевой и ±1,5 с.

## 6. Ограничения и известные ошибки

- Не проверяется то, чего не видно: документы, проводки, суммы, сверка. Сервис формулирует результат как «признаки возможного нарушения»; решение — за проверяющим.
- Мелкие объекты (купюра в кулаке) и перекрытие людьми снижают точность; помогает крупный план зоны кассы.
- Новые типы нарушений распознаются по описанию правил и общей логике; уверенность в них ниже, тип может быть «Иное».
- Склонность модели к ложным срабатываниям частично гасится перепроверкой и голосованием; пороги подобраны на отложенной части датасета.
- Звук не используется; лица не распознаются.
- Детерминированные правила (телефон по детектору YOLOX, посторонний в служебной зоне) Qwen может только отклонить уверенным «нет»; ошибка детектора без вето Qwen даёт ложную тревогу — частота проверяется на датасете.
- Текст в кадре модель может прочитать; инструкции из кадра не выполняются — модель выбирает только тип из каталога, норму подставляет код.
- Время обработки зависит от длины видео и GPU: 24 ГБ — 1,5–3 мин на 145 с.

## 7. Безопасность данных и файлов

| Угроза | Мера |
|---|---|
| Передача видео в облачные AI | все модели внутри сервиса; vLLM слушает только 127.0.0.1 (в compose — только внутренняя сеть); `HF_HUB_OFFLINE=1`; `selftest.py --offline` — 0 внешних соединений |
| Доступ к API без права | ключ `X-API-Key` (≥16 символов, сравнение за постоянное время), без ключа — 401; сервис не стартует со слабым ключом или `change-me` |
| Чужой результат по угаданному адресу | job_id — 96 бит случайности; задачи жюри и сайта разделены: сайт не видит результатов жюри, API — задач сайта |
| Копии тестовых видео | видео с разметкой для задач жюри не создаётся; `/results/…` отдаёт только видео загрузок с сайта |
| Забить очередь и сорвать лимит 5 минут | видео жюри обрабатываются первыми (память и Redis); у сайта лимит 3 ожидающие загрузки и 10 в час с адреса (429) |
| Вредный файл | лимит 200 МБ потоком, проверка «это видео» до очереди, длительность ≤ 15 мин; имя файла на диске не используется |
| Обход путей | job_id проверяется по шаблону; файлы пишутся только в свои папки |
| Хранение тестовых видео | исходное видео удаляется сразу после анализа (или после разметки для сайта); задачи старше 72 ч удаляются целиком; `tools/wipe_data.sh` — полная очистка после хакатона |
| Доступ к файлам на сервере | папки данных 700, файлы 600, файл ключа 600 |
| Перехват трафика | HTTPS через прокси RunPod (или Cloudflare Tunnel) |
| Встраивание / XSS | CSP, X-Frame-Options DENY, nosniff, no-referrer; текст модели экранируется; результаты `no-store`; решения проверяющего валидируются |
| Утечка подробностей ошибок | пользователю — понятная причина, трассировка — только в журнале |
| Персональные данные | лица не распознаются и не идентифицируются; роли — по положению и действиям |

Сайт по ТЗ работает без входа (FAQ 27), поэтому загрузки с сайта защищены лимитами, а не паролем.
Порт 8888 (Jupyter шаблона RunPod) на время проверки закрыть в настройках пода.
